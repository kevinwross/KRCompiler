# 0061 — Function definition location and an entry label

- Status: accepted (2026-11-24)
- Date: 2026-11-24
- Decision: `ir::Function` carries the source location of its definition. Every
  backend emits a `.L<symbol>.begin` label at the function symbol address, before
  the prologue, and an `L` bridge record for it when the location is valid.
- Scope: IR metadata, the KR32/KR16/KR216 debug bridge, and one label in the
  KR232 assembly. No object, symbol, ABI, or KDBG record format changes.

## Context

A function's symbol is a label at its entry, but the debug bridge's first line
record comes from the first instruction that carries a source location. In the
KR32 backend the prologue is emitted before the entry block, so that first record
sits after `PUSH`/`ADJSP`/`LEA` and after the parameter stores. For
`int add(int a, int b) {` on line 1, the first `.Ldbg` record names line 2 at an
address inside the body; no line record names line 1 at all.

A debugger resolves a breakpoint on the definition line by finding a line record
for it. Without one, a breakpoint on `{` either fails to bind or binds to the next
line. It also cannot stop before the prologue, so the call frame's creation
(`PUSH`, frame-pointer setup, stack adjustment) is never observable as its own
step.

The definition line is front-end knowledge. IRGen has the `FunctionDefinition`
AST node, with its location, but `ir::Function` keeps no source location; it is
discarded when the body is lowered. No backend can recover it from the first
instruction, which is a later statement by construction.

## Decision

`ir::Function` gains:

```cpp
DebugLocation definition;
```

`CIRGen::generate_function` sets it from the `FunctionDefinition` node's
`location`, through the source manager, before it lowers the body. A synthesized
function (a global-initializer wrapper, a thunk, an instantiated helper with no
source body) leaves it invalid.

Each backend that builds a textual bridge emits, immediately after the function
symbol:

```asm
add:
.Ladd.begin:
        PUSH R7
        ...
```

and, when `function.definition.valid()`, an `L` record naming that label with the
definition's file, line, and column. The record goes through the same source
table and label-resolution path as every other line record, so the linker
resolves it to the function's address exactly as it resolves the symbol.

The function's `F` record keeps the symbol as its start. The symbol and
`.L<symbol>.begin` are at the same address, so the function span and the new line
record agree, and a reader that only knows the symbol needs no change.

The label is emitted for every function, including one with no definition
location, so a disassembly shows one stable entry marker before the prologue. Only
the line record is conditional.

KR232's bridge is generated by its assembler from the assembly text, not from IR
debug locations, so that target gets the `.L<symbol>.begin` label but no
definition-line record until its assembler accepts source line information. This
is a known gap, not a claim.

## Consequences

- A breakpoint on a function's definition line binds to the first byte of the
  function, before the prologue, on KR32, KR16, and KR216.
- Stepping from that breakpoint shows the frame being created: the saved frame
  pointer, the stack adjustment, and the parameter stores.
- Every compiled object's debug section gains one line record per function, and
  every assembly output gains one label per function. Code bytes and addresses do
  not change; `.text` sizes and all executable addresses stay identical.
- The definition location is metadata: it has no dataflow, no verifier rule, and
  no effect on a pass.
- IR dumps do not print it; the field exists for backends.
- KR232 needs a follow-up in its assembler to carry source lines before the same
  breakpoint works there.

## Alternatives considered

**Derive the line from the first instruction's debug location.** Rejected: the
first instruction with a location is the first statement, which is a later line,
and the prologue precedes it. A breakpoint would bind after the frame exists.

**Add an IR marker instruction at the entry.** Rejected: every pass, the verifier,
and the dump would have to handle an instruction that produces no code, for one
piece of metadata that belongs to the function as a whole.

**Put the location in the function's debug display name.** Rejected: the display
name is a name, is emitted as a name, and is used for symbol resolution by
identity; encoding a line into it would corrupt both.
