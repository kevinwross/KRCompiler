## 1. Purpose

Make the four VM trees build the same way, make the compiler able to produce the guest binaries they embed, and make adding the next four architectures cheap.

The outcome is four uniform statements, true in every repository:

```text
cmake --preset <host>-<config>          # one preset vocabulary, all trees
cmake --build --preset <host>-<config>
ctest --preset <host>-<config>
pwsh scripts/gate-windows.ps1           # or scripts/gate-linux.sh
```

and one new capability in the compiler:

```text
krc image --target kr32 --base 0x00010000 --flat -o init.bin objects...
```

## 2. Current state, measured

### 2.1 Four build styles

| | kr32 | kr16 | kr232 | kr216 |
|---|---|---|---|---|
| Windows generator | Visual Studio 18 2026 | Visual Studio 18 2026 | **Ninja** | Visual Studio 18 2026 |
| Configure presets | `windows-msvc` (+ debug/release *build* presets) | `windows-vs2026`, `windows-ninja` | `windows-msvc`, `linux-wsl`, `linux-arm64` | `windows-msvc-debug`, `windows-msvc-release` |
| Guest compiler | `find_package(krc-toolchain)`, links `krc::toolchain` | own in-tree compiler by default (`KR16_TOOLCHAIN=builtin`), package optional | `krc`/`krld` executables (`KR232_KRC`) | bundled `dist/external/kr216-toolchain`, or `KRC_EXECUTABLE` |
| Build wrapper | none | none | none | `build.cmd` |
| Embedded guest artefacts | committed `bios.k32`/`kernel.k32`, 8.7 KB and 185 KB | `embedded_libc.cpp`, generated by Python and committed | kernel compiled at build time by `krc`, fixture committed | none |

`kr32`, `kr16` and `kr216` are visual-studio trees whose presets cannot name the same build twice; `kr232` is a Ninja tree with a single untagged configuration. A command that works in one repository is not the same command in another, and a gate result means something slightly different in each.

### 2.2 The OS build path is broken today

`kr32os/build.ps1` drives the guest build through the `kr32` executable in 59 invocations: 20 × `cc`, 28 × `as`, 11 × `ld`, with flags `--flat`, `--base`, `--sym`, `--map`, `--source-id`, `-S`, `--object`. Those verbs have been removed from the CLI — `src/cli/cli.cpp:960-1015` dispatches `dis`, `vm`/`run`, `os`, `size`, `debug`, `shell`, `dap` and nothing else:

```text
$ kr32 ld
kr32: unknown command 'ld'.
$ kr32 cc
kr32: unknown command 'cc'.
```

`scripts/update-os.ps1` fails at line 59 when it calls that script, so the committed `kernel.k32` cannot be regenerated by anything in the tree. `kr32os/CMakeLists.txt` is `project(KR32OS NONE)` with a custom target that shells out to the same broken script, and `CMakeLists.txt:127` only *errors* when the image is missing.

`tools/krc_image` is not the replacement: 140 lines, `--source`, `--output`, `--cxx`, one source and one image. Its own header says the test suite uses it "so the C/C++ examples still have an image to run while KR32's built-in compiler is being retired".

### 2.3 The linker is closer than the driver

`krld --help` already offers `--target`, `--entry`, `--base`, `--map`, `--layout`, `--source-root`, and assembles `.s` inputs. Missing for the OS build: `--flat` (raw bytes at base, documented for the `.sym` consumer in `kr32/include/kr32/os/symbols.h:14`), `--sym` (symbol sidecar), and `--source-id` (debug source numbering that `krc` does not have).

### 2.4 krdbg consumes the VMs two different ways

| Adapter | How it consumes the VM |
|---|---|
| `krdbg_kr232` | *compiles* `${KRDBG_KR232_ROOT}/src/{decoder,devices,frame,loader,machine,memory}.cpp` |
| `krdbg_kr216` | *compiles* kr216's `decode, disasm, encoding, image, machine` |
| `krdbg_kr16` | *links* `kr16_core` |
| `krdbg_kr32` | *links* `kr32_core kr32_container kr32_dis kr32_os_images` |

The same target is consumed two ways, so a VM's core has no single interface, and the debugger can be built against a different translation of the machine than the emulator uses.

### 2.5 Guest artefacts drift when they are committed

Within one week, four sets of committed guest binaries were found stale against their sources: kr232's `kernel.k232` and `kernel-gate.bin`, kr232's seven fixtures, krdbg's five fixtures and its adapter hash, and kr16's release-policy row (which asserted a workflow file that had been deleted). Each was caught only because a check existed; the OS images have no such check at all.

## 3. Decisions

**D1 — the embedded-artefact pipeline lives in krcompiler.** The compiler owns compiling, linking and packing guest objects; every VM consumes it and none reimplements it. `krld` grows `--flat` and `--sym`; the `krc` family grows a multi-input image command. *(Owner decision.)*

**D2 — one switch, krc default, alternatives supported.** Every VM takes the same toolchain option. `krc` is canonical. kr16's in-tree `builtin` compiler and kr216's bundled toolchain remain supported backends, documented as alternatives with their own tests, not deleted and not parallel code paths. *(Owner decision.)*

**D3 — Ninja is the gate generator; Visual Studio presets exist for IDE users.** Debug information is produced by `cl.exe`, not by the generator: the Ninja tree at `kr232/build/windows-msvc` contains `kr232-emu.pdb` and `kr232_tests.pdb`, and the Visual Studio tree at `kr32/build/windows-msvc` contains `kr32_core.pdb` and others. The Visual Studio debugger reads those PDBs either way; what differs is that a Ninja tree has no `.sln`, so Visual Studio must open the folder through its CMake integration (`CMakePresets.json`) rather than a solution. Both presets therefore exist in every repository, and the gate runs the Ninja one. *(Owner decision.)*

**D4 — krdbg consumes VM cores through exported CMake targets, in phase P2.** Each VM exports `<vm>::core` (and any sibling targets it needs), and krdbg links them, so all four adapters are built the same way. *(Owner decision.)*

**D5 — an image's extension names its target; commands suggest it, readers never require it.** Every runnable image is `*.kr32`, `*.kr16`, `*.kr64`, `*.kr216`, `*.kr232`, replacing `.k32`, `.kex`, `.k232` and `.k216`. Objects follow the same shape, `*.krNN.kro`, so a directory listing never mixes targets: `program.kr32.kro`, `program.kr232.kro`. Flat link output — the kr32 boot pair's raw form, user images loaded at a base — takes `*.flat`, so that "which machine" and "container or raw" stay two axes and not one. Sidecars take `*.sym` and `*.map`.

The container already carries a target id and the loaders already check it (`kr232/src/loader.cpp:93` rejects anything but 5; `kr216/src/image.cpp:77` rejects anything but 4), so the extension is advisory for machines and load-bearing only for people and scripts. That is exactly why the tools must refuse a name that disagrees with the container: an advisory name that is never checked becomes a wrong name that is never noticed.

People name things `program.kr32.backup` and `program.kr32.didnotwork`, and a loader that refuses them is fighting the user. The rule is therefore asymmetric on purpose:

- **Reading.** A file is identified by its header. A path with an unknown suffix is accepted without comment. A path whose final suffix is a *known* target extension that contradicts the header is refused, naming both. A directory scan — krdbg's demo, kr16's CLI file picker — looks only at known extensions, because that is where the name is all it has.
- **Writing.** With `-o` omitted, or given a name with no suffix, the tool appends the target's extension: `--target=kr32 -o program` writes `program.kr32`. With an unknown suffix it writes where told and says nothing. With a known suffix that contradicts `--target` it refuses. `--help` and every usage line show `.krNN`, so the convention is visible before the first mistake.

No aliases: `.kex` and `.k32` are deleted in the same phase, because nothing has shipped and a compatibility name is a drift that starts on day one.

**D6 — the dependency direction is a rule, not a convention.** The compiler never links a VM; a VM never builds guest artefacts by invoking itself; the debugger never compiles a VM's sources. A repository that needs another's code consumes an exported target or a produced file, and every such edge appears in §3.1.

### 3.1 The target graph

```text
krcompiler     krc (driver)  krld (linker)  krcimage (packs)   krc::toolchain  krc::debug
   │                │              │              │
   │                └──────────────┴──────────────┘
   │                        guest artefacts: .k32/.kex/.kro/.bin/.sym/.map
   ▼
kr32::core  kr16::core  kr232::core  kr216::core      (+ ::container, ::dis, ::images)
   │
   ▼
krdbg          adapters link the four ::core targets
```

Build order is the graph's topological order: **krcompiler → the VMs → krdbg**. Nothing in a VM's build invokes a VM executable, and nothing in krdbg compiles a VM's sources.

**D7 — the toolchain renders one listing format.** The data already exists and its ownership is the problem. `krc::toolchain` carries `ListingRow` — section, statement address, encoded bytes, statement text, and the source line a preceding `.Ldbg` attributed it to — and deliberately declines to choose a layout: "A host renders its own `.lst`: the two VM front ends disagree on the format and keep their own" (`include/krc/toolchain.h:133`, restated in `docs/toolchain-embedding.md:121-127`). The consequence is three states: kr32 documented `kr32 as --listing` in its programmer's reference, but that verb is gone; kr16's `-l` writes `hello.lst` (`docs/curriculum.md:24`); kr232 has nothing; kr216 records a compiler-listing comparison as still open. Since nothing has shipped, the renderer moves into the compiler as `krc::listing`, `krc -l` writes `.lst`, and every host that offers a listing calls it. One layout, one renderer, byte-identical on every host — the same argument as D5.

The `.lst` is a **composed document for reading**, never an input to any tool, and never parsed by one. That frees the layout to be human-first — aligned columns, labels on their own rows, blank lines between sections — and it sets the contents: a header (tools and versions, target, source files, image, entry, base), a section table with final addresses and sizes, the statement rows with encodings, labels, a symbol table, and the placement summary that `--map` also writes. One file, because a reviewer who has to open a second file to learn where a section landed will eventually not bother. The `.map` stays as a standalone artefact for scripts; both render from the same data, so they cannot disagree.

**D8 — generated assembly names its target twice: in the file name and in a directive.** `krc -S` already opens with a comment naming the machine (`; kr232 backend, optimization level 0`, `; KR32 assembly generated by krc`), and that comment is the only place the fact appears — unchecked, unparsed, and phrased differently per backend. Two changes make it load-bearing.

*The name:* generated assembly is `<stem>.krNN.s`, so `program.kr32.s` sorts beside `program.kr32` and `program.kr32.lst` and a directory listing reads as one family. Not `.Skr32`: the type belongs in the final suffix, uppercase `.S` already means "needs preprocessing" in the wider world and in this tree (`kr32os/bios/entry.S` is exactly that), and mixed case collides on a case-insensitive filesystem.

*The directive:* generated assembly carries `.target krNN` as an assembler directive near the top. An assembler given a file whose directive contradicts `--target` refuses it, naming both values; a file with no directive assembles as before, so hand-written sources stay valid. This is the D5 rule applied to source: the name is a hint, the content is the fact — and the content travels through renames, so a `program.kr32.backup` holding kr232 code is caught. Directives are a toolchain contract rather than ISA text (no ISA draft specifies `.text` or `.globl`), so no draft revision is needed. It also forces the current divergence to settle: kr232 emits `.globl` where kr32 emits `.global`.

**D9 — three platforms, and Linux x64 builds from an ext4 mirror, never from the Windows mount.** The inner loop is Windows x64 debug. Before a merge, two more rows prove the family: Linux x64 through WSL and Linux ARM64 on BitWhiz over SSH. A WSL build on `/mnt/c` is the one configuration not allowed: `kr232/scripts/wsl-mirror.sh` exists because "a WSL build on /mnt/c carries host paths in its debug data and its timestamps are too coarse for an incremental build", and it rsyncs the checkout to `$HOME/mirrors/<repo>` excluding `build/`.

That solution sits in one repository and is remembered by one gate script. The other five trees have neither a mirror nor a check, so a Linux gate run from `/mnt/c` builds on the mount and reports green. This session did exactly that: the compiler's Linux gate ran as `wsl -e bash -lc 'cd /mnt/c/Users/kevin/repos/krcompiler && …'` and passed 958 of 958 with 3704 assertions, on the wrong filesystem. The mirror is a build-confirmation tree and carries no history: `.git` is excluded, so it cannot be mistaken for a checkout and cannot be committed from.

The fix is to make the mirror the *only* way a Linux gate builds: the gate detects that its source root is under `/mnt/`, refreshes the mirror, and re-executes itself from there; `--in-place` opts out for a host whose tree is already native.

**D10 — the compiler is the root of the dependency graph, so a change to it rebuilds every host and every guest artefact.** `krc`, `krld` and the assembler produce every object, image, listing and embedded binary in the family, and every VM and the debugger link against the package or consume its output. There is no partial answer to "the backend changed". Everything else selects: a change confined to kr232's tree rebuilds kr232 and krdbg, a change to krdbg rebuilds krdbg alone. §4 J1 is the table.

**D11 — two stamps with two different jobs, and neither goes into the bytes.** Compatibility needs an ordered integer: `KRC_ABI`, bumped when a convention moves — variadic slots, struct passing, the container layouts — checked by every loader, which refuses an image stamped with a different value and names both. Provenance needs an identity: a UTC build timestamp printed by `krc --version` and recorded in the gate log, so a green result names the compiler that produced it. A timestamp is the wrong compatibility token — clocks skew, and "built later" is not "compatible" — and it is the wrong thing to embed in an image, because kr232 has a determinism row that byte-compares two builds and every fixture hash would move. If an artefact must carry identity, it carries a hash of its inputs, which stays reproducible; the clock stays in the log.

**Carried defect P1-0 — the rebuilt kernel panics.** The compiler's kernel reaches the banner and then faults (vector 4, `pc=0x150632`); the committed kernel boots. One misconception is now settled and worth recording, because it cost two rounds: kr32os writes its vector table with **byte offsets**, not indices (`VECTOR_TIMER 64` is slot 16, `VECTOR_PAGE_FAULT 16` is slot 4), and the machine delivers IRQ line *n* as vector `16 + n`. **P1-0: the emitted order is the defect, 2026-11-27.** `register_allocator.cpp` assigns each value a register and the backend's `load_value` inserts the copy needed to reach the requested register. In the failing access the emitted order is: `LOAD R8, [R7 + 8]` (the index, materialised in its allocated register), then `MOV R8, R9` (the base copied into that same register), then `MOV R1, R8` and `MUL R1, R1, #48` -- so the index is materialised first and the base copy then lands on it. The GEP case emits the base load *before* the index load, so this order cannot come from it directly; the copy that destroys the index is the one `load_value` adds when the base's allocated register differs from the requested one, and the destination it chooses is the register the index is still live in. The fix is to have that copy respect the index's live range -- spill or pick another register -- and the reproducer at `build/spawn-min` says when it is right.


**P1-0: the lowering is correct, the allocator is not, 2026-11-27.** `kr32_backend.cpp`'s `GetElementPtr` case (`src/backend/kr32_backend.cpp:1972`) does the right thing: it loads the base into the result register, loads a runtime index into `R1` through `load_low_word`, multiplies `R1` by the stride, and adds `R1` to the result register. What the failing assembly shows instead is the index arriving in `R8` and a `MOV R8, R9` copying the base over it -- a move the GEP case never emits. So the corruption is introduced after lowering, by the pass that assigns physical registers and inserts the moves the lowering relies on: it places a copy into a register that still holds a live operand. That is the boundary to work at, and the reproducer at `build/spawn-min` is the oracle.


**P1-0 minimised to one access, 2026-11-27.** With pid stored as a constant, the scan and the two stores compile correctly and only the *final read* is wrong. In the same function, three accesses compute `table[index].field`:

```
.Ldbg.spawn.27  LEA  R9, [table]      .Ldbg.spawn.33  LEA  R9, [table]      .Ldbg.spawn.39  LEA  R9, [table]
.Ldbg.spawn.28  LOAD R10, [R7 + 8]    .Ldbg.spawn.34  LOAD R10, [R7 + 8]    .Ldbg.spawn.40  LOAD R8,  [R7 + 8]
                MOV  R1, R10                  MOV  R1, R10                  MOV  R8,  R9
                MUL  R1, R1, #48              MUL  R1, R1, #48              MOV  R1,  R8
                ADD  R9, R9, R1               ADD  R9, R9, R1               MUL  R1,  R1, #48
                                                                            ADD  R8, R8, R1
```

The first two are correct. In the third, the index is loaded into `R8` and then `MOV R8, R9` copies the *base* into the same register, destroying it; the multiply then scales the base instead of the index. The difference between the three is only which register the index load landed in -- when it lands in the register the base is about to be copied into, the copy wins. That is a register-allocation defect in the address expression `base + index*scale`, and it is the smallest form of the kernel's `table + table*48`.

**P1-0 root cause found, 2026-11-26: the address of `table[index]` is computed as `table + table*48`.** The `-O1` code for the failing access is five instructions, and the second one throws away the index:

```
0x24F60  LEA  R9, [0x00028dfc]   ; R9 = &table
0x24F68  LOAD R8, [R7 + 20]      ; R8 = index
0x24F6C  MOV  R8, R9             ; R8 = &table   <- the index is destroyed
0x24F74  MUL  R1, R1, #48        ; R1 = &table * 48
0x24F78  ADD  R8, R8, R1         ; R8 = &table + &table*48
0x24F8C  LOAD R8, [R0]           ; faults
```

The arithmetic confirms it exactly: `0x28DFC + 0x28DFC*48 + 4 = 0x7D2D40`, which is the FAR the panic has been reporting all along. The load at 0x24F68 is dead code because the next instruction overwrites its destination; the compiler should have multiplied the *index* by 48 and added the base, and instead multiplied the base by 48 and added the base. Everything else about P1-0 follows from this one instruction: it happens only at `-O1` because only the optimiser coalesces these temporaries; the standalone fixtures pass because their address computations did not take this shape; and the panic's address moved on every rebuild because `&table` moved. The fix belongs in the register allocator's handling of the address expression `base + index*scale`, and it needs a reproducer built from *this* statement sequence rather than the loop around it.

## 6. Adding architecture number five

The plan is only worth its length if the next VM is cheap. After P5, a new VM costs:

1. `krcompiler`: a `TargetProfile` entry, a backend, a target id, an ADR — the existing `new-target-guide.md` process, unchanged.
2. New tree from a skeleton: `CMakeLists.txt` with `find_package(krcompiler)` + `include(KrGuest)`, two presets, `::core` export, a gate script, a fixture generator, and a drift row.
3. `krdbg`: one adapter linking `<vm>::core`.
4. `kr232/scripts/check-family.ps1`: one line.

Target: **under a day**, with the guest-artefact half already available from `krc image`.

## 7. Risks

| Risk | Mitigation |
|---|---|
| `krld`'s container bytes differ from kr32's old writer, so the VM will not boot | P0 compares rebuilt images against the committed ones byte for byte before anything is deleted |
| Debug information regresses under a single generator | PDBs are generator-independent (§3 D3); the gate runs both presets in P2 |
| kr16's `builtin` path rots once it is not the default | it keeps its own gate row, and D2 requires it to pass in every phase |
| The preset rename invalidates every existing build tree on every machine | one documented `--fresh` per tree; the old names are removed in one commit, not kept as aliases |
| krdbg's golden hashes move when the build changes | fixtures are regenerated by script (E1), with the reason recorded per commit, as with the alloc-bit fix |
| ARM64 gate drifts from the Windows gate | F2 asserts row counts on both hosts |
| Two agents refresh one mirror while a third builds it | one lock per mirror (I3); the mirror is disposable, so a failed refresh is deleted and repeated rather than repaired |
| Agents follow stale docs | each phase updates `AGENTS.local.md` in every repository in the same commit |

## 8. Non-goals

- Retiring kr16's in-tree compiler or kr216's bundled toolchain (D2 keeps both).
- Replacing CMake, or introducing another build system.
- Changing any instruction encoding, ABI or debugger behaviour.
- Merging the repositories.

Every question was answered by the owner on 2026-11-23. The decisions they produced are in §3; this section records the reasoning so a later reader does not reopen them by accident.

| Question | Answer | Where it landed |
|---|---|---|

| Checked-in binaries? | A provenance manifest naming each artefact's source and hash, with a check | J7 |

## 10. Definition of done

- The four preset names resolve identically in kr32, kr16, kr232, kr216, krdbg and krcompiler.
- `krc image` produces every embedded guest binary in the family; no VM invokes itself to build its own resources.
- krdbg links four `::core` targets and compiles no VM source.
- Every fixture has a generator and a drift row; `ctest -j 8` is green three times in each repository.
- Generated assembly carries its target in both its name and a validated `.target` directive.
- One listing format, rendered by `krc::listing`, offered by every host that assembles or builds guest code, and composed so that a build can be understood from that one file.
- One extension per target: `<stem>.krNN` for images, `<stem>.krNN.kro` for objects, `.flat` for raw output, `.lst` for listings, and no tool that dispatches on a hardcoded list.
- A Linux gate never builds on `/mnt/c`: it mirrors, re-executes from the mirror, and says which path it used.
- One family command builds and gates Windows and ARM64 in graph order.
- The selection table in J1 decides what a change runs, and the full matrix is one command.
- A green result names the compiler that produced it, and a loader refuses an image built for a different ABI.
- A release archive is built twice, compared, and ships with checksums.
- Every repository fails early, by name, when a host tool is missing.
- A fifth VM has been added once, from §6, in under a day.
