## Non-conforming profile

The IP16 profile is deliberately non-conforming: 16-bit `long`, no `long long`, no floating point. Code that assumes 32-bit `long` must use `int32_t`/lo-hi structures or be adapted. Every diagnostic that depends on the profile must say so.

A type the profile cannot represent is rejected where it is named — `'long long' is not supported by the kr16 profile`, and the same form for `float`, `double`, and `long double` — instead of being lowered to a zero-width integer or to `f32`/`f64`. The shared headers carry the matching guards: `<stdlib.h>` omits its 64-bit and floating-point conversions, `<math.h>` omits every declaration, and `<time.h>` omits `difftime`, all under `__kr16__`, so including them stays usable on the profile.

## Code generation notes

- 16-bit little-endian; 16/32-bit instruction forms; 64 KiB address space.
- R0–R4 plus SP/SR/PC; R4 frame pointer; R0 return; R1–R3 arguments.
- Stack alignment 2 bytes; aggregates by value on the stack; varargs on the stack.
- Branches come in two widths. The **B-type** is one word: `0111 cond disp8`,
  a signed word displacement with a target of `PC + 2 + disp8 * 2` and a reach of
  -256..+254 bytes. `BRA` is condition 14, and `BEQ`/`BNE`/`BGE`/`BLT` and
  the rest share the encoding. `encode_b` emits it and the backend already uses it
  for conditionals. `JMP` and `CALL` are the two-word C-type with a 16-bit
  signed word displacement and 64 KiB reach. There is no one-word `JMP`.
- Relaxation is therefore **available**, not blocked on the ISA: an unconditional
  branch could be `BRA` where the backend currently emits `JMP`. Two things are
  missing on this side -- the backend does not select `BRA`, and the assembler
  does not promote an out-of-range `BRA` to `JMP` the way the sibling assembler
  does. Both are recorded as work, not as an ISA gap.
- Tight code-size budget: section GC and size-oriented peepholes matter.
- C and C++ both compile for KR16 within the profile's limits — no `long long`,
  no floating point, and aggregate parameters by value are rejected. Whether C++
  is *supported* on KR16, rather than merely working, is still an open decision.
